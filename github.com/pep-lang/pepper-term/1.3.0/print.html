term

Interactive terminal programs: raw mode, key and mouse input, bracketed paste, the clipboard, line editing with history, cursor control, and 16, 256 and true colors, on Linux, macOS (termios) and Windows (the Console API).

Bring it in with import term. Decoding input (InputDecoder) and editing lines (LineEditor) are pure, bytes in and events or text out, so they work and test without a terminal. Without one (input or output a pipe or a file), raw mode does nothing, lines are read plainly, and colors_enabled() is false.

  • RawMode, restore: raw mode on and off; the terminal is restored at exit and on a panic too
  • KeyReader, KeyDecoder, KeyEvent, Key: key presses
  • MouseMode, MouseTracking, PasteMode: mouse reporting and bracketed paste on and off (both are off unless a program turns them on)
  • InputReader, InputDecoder, Event, MouseEvent, MouseKind, MouseButton: key presses, mouse reports and pastes together
  • Clipboard, ClipboardBackend, ClipboardError: copying to and reading from the clipboard, the OS's or the terminal's (OSC 52)
  • LineReader, LineInput, LineEditor, EditStatus, History: readline-style line editing
  • Style, Color, BasicColor, RESET, colors_enabled: colors and text styles
  • move_to, move_up and the other moves, CLEAR_SCREEN and the other sequences: the cursor and the screen
  • input_is_terminal, output_is_terminal, size, Size: the terminal itself

Example

import term;
import [BasicColor, Color, LineInput, Style] from term;

main(): int {
    var prompt = Style(foreground = Color.Basic(BasicColor.Green), bold = true);
    var reader = term.LineReader();
    while (true) {
        match (reader.read_line(prompt.paint("> ", term.colors_enabled()))) {
            Line(text) => {
                print($"you typed {text}");
            }
            Interrupted => {}
            EndOfInput => {
                return 0;
            }
        }
    }
}

ClipboardBackend

enum ClipboardBackend

Where a Clipboard copies to and reads from.

Cases

Auto

Auto

System when the program runs locally and the OS has a clipboard it can reach, else Osc52. Locally means none of SSH_CONNECTION, SSH_CLIENT and SSH_TTY is set: over SSH the OS's clipboard is the remote machine's, which the user cannot paste from.

System

System

The OS's clipboard: on Windows, its own (CF_UNICODETEXT); on macOS, pbcopy and pbpaste; on Linux, wl-copy and wl-paste when WAYLAND_DISPLAY is set, else xclip or else xsel when DISPLAY is, each found on the PATH.

Osc52

Osc52

The terminal's: OSC 52 sequences written to standard output, which the terminal acts on, so it reaches the user's clipboard over SSH.

Clipboard

struct Clipboard

Copies text to the clipboard, and reads it, through the backend backend says (see ClipboardBackend): the OS's clipboard, or the terminal's through OSC 52. Auto, the default, is resolved once, when the Clipboard is made, so backend says which is in use.

Through OSC 52, copy writes ESC ] 52 ; c ; <base64> BEL to standard output, and the terminal sets its clipboard; nothing comes back to say whether it did. Most terminals allow it, some only after the user turns it on, and some cap its length (osc52_limit). read asks with ESC ] 52 ; c ; ? BEL, which most terminals refuse by not answering, so it waits at most timeout_ms and then fails with ClipboardError.TimedOut; it never hangs.

Inside tmux, the sequence reaches tmux, not the terminal: with set -g set-clipboard on in .tmux.conf, tmux sets its own buffer and passes the copy on to the terminal. GNU screen passes OSC 52 on only inside its own escape (ESC P ... ESC \) and cuts long ones short. This package writes the plain sequence and wraps it for neither, since tmux's set-clipboard makes that unneeded; under screen, use System.

The text copied or read is never put in an error or a log.

Example

import term;
import [ClipboardBackend] from term;

main(): int {
    var clipboard = term.Clipboard();
    var copied = clipboard.copy("hello");
    if (copied.is_err()) {
        print($"could not copy: {copied.error()}");
        return 1;
    }
    print(clipboard.backend == ClipboardBackend.System ? "copied" : "asked the terminal to copy");
    return 0;
}

read

read(timeout_ms: int = 1000, input: InputReader = InputReader()): Result<String, ClipboardError>

Returns the text on the clipboard.

Through OSC 52 it asks the terminal, in raw mode (turned on while it waits, if it is not on), and waits at most timeout_ms for the answer, which input decodes. Other input that comes meanwhile, such as keys, stays in input for its next read, so pass the program's own InputReader. An answer that comes after the wait arrives there as an Event.ClipboardReply. A terminal that asks the user first (kitty can) may answer after the wait; with raw mode off by then the terminal shows the answer as typed text, so for such a terminal keep a RawMode on and pass a longer timeout_ms.

Parameters

  • timeout_ms — how long to wait for the terminal's answer, in milliseconds; the OS's clipboard answers at once
  • input — the reader the terminal's answer is read through

Returns

  • the text, empty when the clipboard holds none; NoBackend when there is no clipboard or, for OSC 52, standard input or output is not a terminal, TimedOut when the terminal does not answer, TooLarge past input's clipboard_limit, or Failed when the OS refused

InputDecoder

struct InputDecoder

Decodes the bytes a terminal sends in raw mode into Events: key presses (see KeyDecoder), mouse reports, in xterm's SGR encoding (ESC [ < b ; x ; y M, or m for a release) and its older X10 one (ESC [ M and three bytes), bracketed pastes (ESC [ 200 ~, the text, then ESC [ 201 ~), and OSC 52 clipboard replies (ESC ] 52 ;, the selection, ;, the text in base64, then BEL or ESC \).

Feed it bytes as they arrive. A sequence split across reads is held until the rest comes, and a lone Escape is held until flush, as with KeyDecoder. A mouse report the decoder cannot read (a button past the third, a position of 0, a broken sequence) decodes as Key.Unknown; huge numbers are capped, never overflow.

A paste is held until its end marker comes, however many reads it takes; pasting says one is under way. Past paste_limit bytes the rest is dropped. When the end marker never comes, flush gives back what was held, the first paste_limit bytes, as the keys it would have been without bracketing.

A clipboard reply is held the same way, up to clipboard_limit bytes of text. One that is not base64, or is cut short by another escape sequence, decodes as Key.Unknown, and so does one whose end never comes, at flush.

Example

import term;
import [Event, MouseKind] from term;

var decoder = term.InputDecoder();
var events = decoder.feed("\x1B[<0;3;4Mx".bytes());
match (events[0]) {
    Mouse(mouse) => assert(mouse.kind == MouseKind.Down && mouse.column == 2, "a click"),
    else => panic("a mouse report"),
}

KeyDecoder

struct KeyDecoder

Decodes the bytes a terminal sends in raw mode into KeyEvents: UTF-8 characters, control characters, and the escape sequences of xterm and its kin (VT100, the Linux console, Windows' virtual terminal input) for the arrows, Home, End, Insert, Delete, Page Up and Down, and F1 to F12, with their modifiers. A mouse report is one Key.Unknown, and a paste the keys its text types; use InputDecoder to read them as they are.

Feed it bytes as they arrive. A sequence split across reads is held until the rest comes. A lone Escape looks like the start of a sequence, so it is held too: when no more bytes arrive soon (a few tens of milliseconds), call flush to decode it as the Escape key.

Example

import term;

var decoder = term.KeyDecoder();
var events = decoder.feed("\x1B[1;5Ax".bytes());
assert(events[0].to_string() == "Ctrl+Up", "an arrow with Ctrl");
assert(events[1].text == "x", "a character");

LineEditor

struct LineEditor

A line being edited: the text, the cursor, and the history that Up and Down move through. handle applies one key; render gives the bytes that redraw the line.

The keys are readline's (Emacs mode):

  • characters insert at the cursor
  • Left, Right, Ctrl+B, Ctrl+F move one character; Ctrl or Alt with Left and Right, and Alt+B and Alt+F, move one word
  • Home, End, Ctrl+A, Ctrl+E go to the start and the end
  • Backspace and Ctrl+H delete before the cursor, Delete and Ctrl+D at it (Ctrl+D on an empty line ends input)
  • Ctrl+W and Alt+Backspace delete the word before the cursor, Ctrl+U everything before it, Ctrl+K everything from it
  • Up, Down, Ctrl+P, Ctrl+N recall older and newer history entries
  • Enter submits the line, Ctrl+C abandons it

Example

import term;

var editor = term.LineEditor();
for (var key in term.KeyDecoder().feed("helo\x1B[Dl\r".bytes())) {
    editor.handle(key);
}
assert(editor.text == "hello", "Left, then insert");
assert(editor.history.entries[0] == "hello", "Enter records it");

sys_posix.pep

The terminal on Linux and macOS, through termios, private to the module. Every platform's file declares the same _term_ functions. The OS's clipboard is reached through the programs that serve it: pbcopy and pbpaste on macOS, and wl-copy, xclip or xsel on Linux.

Source: sys_posix.pep

sys_windows.pep

The terminal on Windows, through the Console API, private to the module. Every platform's file declares the same _term_ functions.

Raw mode turns on virtual terminal input, so the console sends keys as the same escape sequences a POSIX terminal does, and KeyDecoder reads both. Mouse reporting reads the console's input records instead, and turns its mouse records into the SGR reports a POSIX terminal sends. Bracketed paste is asked for with the same sequence as on POSIX, which Windows Terminal answers; the older console host types pastes as keys. The clipboard is Windows' own, as CF_UNICODETEXT.

Source: sys_windows.pep

terminal.pep

The terminal itself: whether the standard streams are one, its size, raw mode, mouse reporting, bracketed paste, and reading keys, mouse reports, pastes and edited lines from it. Each part degrades when there is no terminal (input from a pipe or a file, output to one): raw mode, mouse reporting and bracketed paste do nothing, keys are decoded from the bytes as they come, lines are read plainly, and colors_enabled is false.

Source: terminal.pep

RawMode

struct RawMode

Raw mode: the terminal hands over each key as it is pressed, without echoing it, editing the line, or turning Ctrl+C into a signal, as an editor or a game needs. Making a RawMode turns it on; exit, or the last reference going away, turns it off again.

Use it in a with block, which turns raw mode off however the block ends. The terminal is also restored when the program ends while raw mode is on: at the end of main, on a panic, and on SIGTERM, SIGHUP, SIGINT or SIGQUIT (POSIX). process.exit ends the program without running exit handlers, so call restore() before it.

In raw mode on Linux and macOS, output is raw too: "\n" moves down without returning to the first column, so write "\r\n".

Without a terminal on standard input, raw mode does nothing and active is false. Raw mode is one setting of the whole terminal, so while one RawMode has it on, another is not active either.

Example

import term;

main(): int {
    with (var raw = term.RawMode()) {
        var keys = term.KeyReader();
        print(raw.active ? "press a key\r" : "not a terminal");
        var key = keys.read();
        if (!key.is_empty()) {
            print($"you pressed {key.value()}\r");
        }
    }
    return 0;
}

MouseMode

struct MouseMode

Mouse reporting: while it is on, the terminal sends mouse presses, releases, the wheel and, as tracking says, moves, which InputReader reads as Event.Mouse. Making a MouseMode turns it on; exit, or the last reference going away, turns it off again. It is off unless a program asks: without it the terminal keeps the mouse, to select and scroll.

Use it in a with block, inside a RawMode's. Like raw mode it is turned off when the program ends while it is on: at the end of main, on a panic, and on SIGTERM, SIGHUP, SIGINT or SIGQUIT (POSIX); call restore() before process.exit.

On Linux and macOS it asks the terminal for xterm's reports in SGR encoding (mode 1006), which every current terminal speaks. On Windows it turns on the console's mouse input, and turns Quick Edit (selecting with the mouse) off while it is on.

Without a terminal on standard input and output it does nothing, and active is false. Mouse reporting is one setting of the whole terminal, so while one MouseMode has it on, another is not active.

Example

import term;
import [Event] from term;

main(): int {
    with (var raw = term.RawMode()) {
        with (var mouse = term.MouseMode()) {
            var input = term.InputReader();
            var event = input.read();
            if (!event.is_empty()) {
                match (event.value()) {
                    Key(key) => print($"key {key}\r"),
                    Mouse(click) => print($"mouse {click}\r"),
                    Paste(text, truncated) => print($"paste {text}\r"),
                    else => {}
                }
            }
        }
    }
    return 0;
}

PasteMode

struct PasteMode

Bracketed paste: while it is on, the terminal marks the start and end of text pasted into it, so InputReader reads each paste whole, as one Event.Paste, rather than as typed keys, and a paste with line ends does not run as one command per line. Making a PasteMode turns it on; exit, or the last reference going away, turns it off again. It is off unless a program asks.

Use it in a with block. Like raw mode it is turned off when the program ends while it is on: at the end of main, on a panic, and on SIGTERM, SIGHUP, SIGINT or SIGQUIT (POSIX); call restore() before process.exit.

It asks for xterm's bracketed paste (mode 2004), which current terminals on Linux and macOS, and Windows Terminal, have. A terminal without it ignores the request, and its pastes arrive as typed keys, as they do in the older Windows console. On Windows it turns on the console's reading of escape sequences, which the request needs.

Without a terminal on standard input and output it does nothing, and active is false. Bracketed paste is one setting of the whole terminal, so while one PasteMode has it on, another is not active.

Example

import term;
import [LineInput] from term;

main(): int {
    with (var paste = term.PasteMode()) {
        var reader = term.LineReader();
        match (reader.read_line("> ")) {
            Line(text) => print($"read {text}"),
            Interrupted => {}
            EndOfInput => {}
        }
    }
    return 0;
}

InputReader

struct InputReader

Reads what the user does from standard input, decoding it with an InputDecoder: key presses and, while a MouseMode or PasteMode is on, mouse reports and pastes. A paste whose end does not come within a second is given back as typed keys.

LineReader

struct LineReader

Reads lines from standard input for a REPL or a prompt, with editing and history (see LineEditor for the keys) when standard input and output are a terminal, and plainly otherwise. While a PasteMode is on, a paste goes into the line whole, line ends and all, without submitting it.

import term;
import [LineInput] from term;

main(): int {
    var reader = term.LineReader();
    while (true) {
        match (reader.read_line("> ")) {
            Line(text) => {
                print($"you typed {text}");
            }
            Interrupted => {}
            EndOfInput => {
                return 0;
            }
        }
    }
}
